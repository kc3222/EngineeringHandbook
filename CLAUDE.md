# CLAUDE.md

Guidance for Claude Code when working in this repository.

## Project

An engineering handbook: short reference pages (1–5 min read each) covering
frontend, backend, data/storage, AI engineering, ML/applied research, and
cloud/DevOps. Public reference material — **not** a personal blog or case
study collection. The full outline lives in `handbook-structure.md` at the
repo root; treat it as the source of truth for scope, area/chapter naming,
and page counts. If a request conflicts with that outline, flag the
conflict rather than silently diverging from it.

## Current status

Site shell is scaffolded (Docusaurus 3 + TypeScript) and the GitHub Actions
deploy is wired up. What exists: a landing page per area (hero, stats, chapter
index), a custom navbar with area switcher, a `⌘K` search palette over the
outline, and light/dark theming. What doesn't: `content/` — no page files have
been written yet, so the docs and blog plugins are switched **off** in
`docusaurus.config.ts`. Turning docs back on means setting `path: 'content'`
with an autogenerated sidebar, and it needs at least one page file to exist
first or the build fails.

`src/data/handbook.ts` mirrors `handbook-structure.md` and is what the UI reads
for area/chapter names and page counts. Update it alongside that file — never
hardcode a count in a component.

## Tech decisions made so far

- **Hosting:** GitHub Pages (project site, e.g. `username.github.io/repo-name`).
- **Deploy:** GitHub Actions, using `actions/upload-pages-artifact` +
  `actions/deploy-pages` on push to `main`. No `gh-pages` branch workflow.
- **Site generator:** Docusaurus (React-based, native page-per-file routing,
  built-in sidebar/search — fits an outline with Areas → Chapters → Pages).
  If this changes, update this file.
- **Language:** TypeScript from the start — scaffold with Docusaurus's
  `--typescript` flag (typed `docusaurus.config.ts`, typed sidebars,
  `.tsx` for any custom components). Don't scaffold plain JS and convert
  later.
- **Backend:** none currently, and none needed for the current scope
  (static reference content). See "Future: auth & progress backend" below
  before adding one.
- **Content granularity:** one markdown file per **page**, not per chapter.
  Do not merge multiple pages into one file, and do not build a
  chapter-splitting parser — page-level files ARE the source of truth and
  the eventual "database of content files."

## Content structure

```
content/
  area-1-frontend/
    01-react-fundamentals/
      01-components-and-props.md
      02-state-and-hooks.md
      ...
    02-nextjs-rendering/
      ...
  area-2-backend/
    ...
```

Directory numbering matches `handbook-structure.md`, which currently
labels these as "Part I–VI" — this repo calls the same level "Area"
instead. Treat "Part" (in that doc) and "Area" (in code/frontmatter) as
the same concept until `handbook-structure.md` is updated to match; don't
introduce a third term. Chapters are numbered 01–22 within their areas.
Keep chapter folder names slug-matched to the chapter titles in that file.

## Page frontmatter (required on every page file)

```yaml
---
title: "Components & Props"
area: 1
chapter: 1
page: 1
readMinutes: 3
---
```

Keep this schema stable — it's what a future migration script will read to
populate a real database. Don't add ad hoc fields without updating this
section.

## Writing conventions

- Audience is general/public reference — no personal anecdotes, no
  "in my experience at X" framing, no company-specific examples.
- Each page should be readable in 1–5 minutes. If a page is running long,
  that's a signal to split it, not to shorten by cutting substance.
- Diagrams and code snippets are encouraged where they clarify a concept.
- Exercises/quizzes are explicitly **out of scope for now** (planned for a
  later phase per Open Items) — don't add them speculatively.
- Prefer explaining tradeoffs over prescribing one "correct" approach,
  especially in the framework-comparison chapters (e.g. Next.js rendering
  strategies, REST vs RPC-ish patterns).

## Future: auth & progress backend

Not being built now — this is here so a future session implements it
consistently instead of improvising. Plan, when this phase starts:

- **GitHub Pages stays as-is.** It only serves the static Docusaurus build
  and has no awareness of a backend — nothing about adding one requires
  restructuring the current deploy setup.
- **Backend is a separate deployment**, not part of this repo's Actions
  workflow. Planned choice: **Supabase** (auth + Postgres + RLS), matching
  the pattern already used on the Clinical Decision Support project —
  reuse that experience rather than evaluating alternatives from scratch.
- **Auth is token-based** (JWT via Supabase Auth), not cookie-based —
  required because frontend (`github.io`) and backend live on different
  origins. Supabase's client SDK (`@supabase/supabase-js`) handles this.
- **CORS** must explicitly allow the GitHub Pages origin on the Supabase
  side.
- **Progress tracking** is a simple `user_id` / `page_id` / `completed_at`
  table shape with RLS scoping rows to their owner — no custom server
  needed for this alone.
- Only reach for a real serverless function (Supabase Edge Functions,
  etc.) if logic goes beyond what client SDK + RLS can express (e.g.
  server-computed aggregate progress). Don't add one preemptively.
- Any public keys needed at build time get injected via GitHub Actions
  secrets → env vars in the existing build step, not committed to the repo.

## Commands

- `npm start` — dev server (serves at `/EngineeringHandbook/`, not `/`).
- `npm run build` — production build into `build/`.
- `npm run serve` — serve the production build.
- `npm run typecheck` — `tsc --noEmit`; the deploy workflow runs this too.

Docker is the zero-setup path and is equivalent for dev work:

- `docker compose up` — dev server on host port 4321 (override with
  `HANDBOOK_PORT`), hot reload via bind mount.
- `docker compose --profile prod up serve` — production build on 4322.

Notes if you touch the Docker setup: `node_modules`, `.docusaurus`, and
`build` are **named volumes** deliberately — the bind mount would otherwise
put macOS-built binaries and host-absolute cache paths in front of the
container's own. The dev command passes `--poll` because bind mounts don't
forward filesystem events on macOS/Windows. Docker is local convenience only;
CI builds on the runner and never uses these files.

## Site shell notes

- `src/theme/Navbar/Content` is a **swizzled eject** of the Docusaurus navbar,
  needed for the three-slot layout (wordmark / centred areas / search +
  theme). It may need reconciling on a Docusaurus major upgrade.
- Area I lives at `/`; the other five are `/backend`, `/data`, `/ai`, `/ml`,
  `/cloud`. Active nav state is computed in `src/components/AreaNav` rather
  than via `activeBasePath`, because the root path would otherwise match every
  route.
- The search palette indexes the outline only. Point it at real page content
  once `content/` exists — the palette UI itself can stay.
