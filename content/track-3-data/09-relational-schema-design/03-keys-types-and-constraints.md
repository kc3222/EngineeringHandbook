## Primary keys: what the identifier costs

Every table needs a primary key. The interesting decision is what kind, and it's
worth deciding once per project rather than per table.

| Choice | Storage | Ordering | Leaks | Generated by |
| --- | --- | --- | --- | --- |
| `bigint` identity | 8 bytes | Sequential | Row count, creation order | Database |
| UUIDv4 | 16 bytes | Random | Nothing | Anyone |
| UUIDv7 | 16 bytes | Time-ordered | Creation timestamp | Anyone |

**Natural keys** — using an email address or an ISBN as the primary key — are
occasionally right and usually not. The failure mode is that natural identifiers
turn out to be mutable (people change email addresses) or non-unique in edge cases
you didn't know about, and by then the value is duplicated across every referencing
table. Use a surrogate key and put a `UNIQUE` constraint on the natural one.

**`bigint` identity** is the standard-conforming form of what used to be written
`serial`, and it's what PostgreSQL's own guidance now recommends:

```sql
create table orders (
    id bigint primary key generated always as identity,
    ...
);
```

Compact, clusters well because new rows sort to the end, readable in logs. Two
narrow costs: the id is enumerable (an `/orders/1041` in a URL tells the world how
many orders exist, and invites trying `1040`), and only the database can mint one,
which is awkward when a client or another service wants the identity before the
insert.

**UUIDs** solve both. The classic objection was index locality: random v4 values
scatter inserts across the whole B-tree instead of appending to one page.
**UUIDv7** — standardised in
[RFC 9562](https://www.rfc-editor.org/rfc/rfc9562.html), which obsoletes RFC 4122 —
fixes that by putting a millisecond timestamp in the high bits, so values sort
roughly by creation time. PostgreSQL 18 ships `uuidv7()` natively; before that, an
extension or the application generates them. What it brings back is that the
creation time is *in* the id, readable by anyone holding it.

**A reasonable default:** `bigint` identity for internal tables nobody outside the
system references, UUIDv7 for anything whose id appears in a URL or crosses a
service boundary. Do not mix within one relationship.

## Types: a short list of defaults

PostgreSQL has a large type system and most of the decisions are already made for
you if you follow a few rules.

**`timestamptz`, never `timestamp`.** Despite the name, `timestamptz` does not
store a time zone — it stores an absolute instant, converting on input and output
using the session's `TimeZone`. `timestamp` stores wall-clock digits with no
indication of where the clock was, so two rows written from two regions aren't
comparable. The exceptions are genuinely local facts: a birthday, a store's
opening hours.

**`numeric` for money, never `float`.** Binary floating point cannot represent
`0.1`, so `float` sums drift. `numeric` is exact decimal arithmetic — slower, and
correct. Avoid the `money` type too: its fractional precision comes from a
database-level locale setting.

**`text` for strings.** `text`, `varchar` and `varchar(n)` perform identically in
PostgreSQL; `varchar(n)` just adds a length check. If the limit is a real business
rule, write it as a `CHECK`, where it's visible next to the other rules and doesn't
need a type change to alter.

**`jsonb`, not `json`.** `json` stores literal text and reparses on every access;
`jsonb` stores a parsed binary form, supports indexing, and deduplicates keys.

`jsonb` deserves a warning, though. It's right for genuinely schemaless data — a
webhook payload retained verbatim, user-defined form fields, a sparse settings bag
— and wrong for fields whose shape you know, because nothing inside a `jsonb`
column can be constrained, foreign-keyed, or typed. A schema that is one `id`
column plus a `data jsonb` column is a document store with extra steps, and the
missing guarantees get rebuilt in application code.

**Enumerated values.** Three options, and the middle one is usually right:

| Option | Add a value | Rename / remove | Constrainable |
| --- | --- | --- | --- |
| `enum` type | `ALTER TYPE ... ADD VALUE` | Painful | Yes |
| `text` + `CHECK` | Edit the check | Edit the check | Yes |
| Lookup table + FK | `INSERT` | `UPDATE` | Yes, plus attributes |

A `CHECK` constraint is the flexible default. Move to a lookup table when the
values need attributes of their own — a display label, a sort order, an
`is_active` flag — which happens more often than people expect.

## Constraints are the point

Everything above is preparation for this. A constraint is a statement that is true
of the data *no matter which code writes it*, and it's the only kind of guarantee
that survives a bug in the application, a broken batch job, or a manual fix applied
under time pressure.

```sql
create table subscriptions (
    id           uuid primary key default uuidv7(),
    account_id   uuid not null references accounts (id) on delete cascade,
    plan         text not null check (plan in ('free', 'pro', 'enterprise')),
    seats        integer not null check (seats > 0),
    started_at   timestamptz not null default now(),
    ends_at      timestamptz,

    constraint ends_after_start check (ends_at is null or ends_at > started_at),
    constraint one_active_per_account unique nulls not distinct (account_id, ends_at)
);
```

Four kinds are doing work there:

- **`NOT NULL`** — the most valuable and most under-used. Every nullable column is a
  branch in every piece of code that reads it. Use it unless the absence of a value
  is itself a meaningful state.
- **Foreign keys** — the guarantee that a reference resolves. Skipping them "for
  performance" trades an index lookup on write for knowing that your data means
  anything.
- **`CHECK`** — arbitrary row-level invariants. `seats > 0` costs nothing and makes
  a whole class of bug impossible rather than merely unlikely.
- **`UNIQUE`** — including across multiple columns. `NULLS NOT DISTINCT` (PostgreSQL
  15+) is the piece people work around for years without knowing it exists: by
  default `NULL`s are all distinct, so a unique index doesn't prevent two rows with
  `ends_at IS NULL`. That modifier makes them collide — which is how you say "at
  most one open subscription per account" declaratively.

For invariants that span rows in a way `UNIQUE` can't express — no two bookings for
the same room may overlap in time — reach for an **exclusion constraint** with
`btree_gist`, which is the same idea generalised to any operator.

## Practical notes

- **Constraint names are an API.** An unnamed constraint gets a generated name that changes if the table is rebuilt. Name them, because application code that maps a violation to a friendly error message is matching on that name.
- **Validate in the application *and* the database.** The application check exists for a good error message and fast feedback; the database check exists because it's the one that's actually true. This is not duplication to eliminate.
- **`NOT VALID` on a big table.** Adding a `CHECK` or foreign key to a populated table scans it under a lock. `ADD CONSTRAINT ... NOT VALID` skips the scan and enforces the rule for new rows; `VALIDATE CONSTRAINT` then checks the existing ones with a much weaker lock. See **Migrations Without Downtime**.
- **Deleting is a business decision.** `ON DELETE CASCADE` on a child that's really a historical record is how a customer deletion silently removes the invoices you're legally required to keep. `RESTRICT` by default; `CASCADE` where the child genuinely has no meaning without its parent.

## What to take away

- Surrogate primary keys; `UNIQUE` on the natural identifier. `bigint` identity internally, UUIDv7 where the id is public.
- `timestamptz`, `numeric`, `text`, `jsonb` — four defaults that resolve most type questions, and `jsonb` only for data whose shape you truly don't control.
- Constraints are the database's contribution to correctness. `NOT NULL` and `CHECK` are nearly free and prevent whole categories of bad row.
- `NULLS NOT DISTINCT` expresses "at most one open record" declaratively; exclusion constraints generalise uniqueness to overlaps.
